## 1. Context & Objective

The iOS app had no native push: out-of-app alerts only reached a phone through ntfy / Pushover /
SMS.  Two agents built the two halves in parallel — the server sender and device registry
(`monet/apns-server`, `c4bd3acb`) and the device half (`monet/apns-ios`, `f697bd32`) — against a
written contract that nothing in either build actually checked.  This branch merges them and makes
the contract real: it is the phase where the halves are made to line up, and where the ways they
could have silently disagreed are turned into failing tests.

Branch `monet/apns-push`, worktree `~/apps/trading-monet-apns`, forked from `origin/main`
(`5784c1cf`).  **This note supersedes and replaces `docs/rollouts/2026-08-12-apns-push-server.md`
and `docs/rollouts/2026-08-12-apns-push-ios.md`, which were deleted in the same commit** (their
content is folded in below; nothing was dropped silently).

## 3. Contract mismatches found, and how each was fixed

The register request and the sign-out DELETE lined up exactly — same path, same verb, same field
names, same `"sandbox"` / `"production"` literals, session cookies as the only auth (identity comes
from middleware's `x-authenticated-user-email`, never the body).  The deep links did not.

### 3.1 The catch-all deep link was unroutable — 17 of 24 event types tapped to nowhere

**The mismatch.**  `pushDeepLink()`'s default arm emitted `https://socratictrade.com/console`.
`DeepLink.destination(for:)` requires `segments.count >= 2` — a path of `/console/<screen>` — so a
one-segment `/console` returns `nil`, `PushPayload.destination` returns `nil`, and the tap handler
returns without routing.  Only 7 of the 24 `NOTIFICATION_EVENT_TYPES` have a specific arm in the
switch; **every other event type** (`block`, `budget_alert`, `storage_warning`,
`prompt_injection_suspected`, `risk_advisory`, `signal_health`, …) hit that default.  The failure
is completely silent: the notification arrives, the tap opens the app, and it lands on whatever tab
was already showing.  Nothing throws, nothing logs.

**The fix** (`src/lib/push-deep-links.ts`): the catch-all is now `/console/activity`.  That is a
two-segment console path the router accepts, it is a real web route so the same URL still works in
a browser, and it is where the notification itself is listed — `app/console/activity/page.tsx`
renders notification events, so an event with no more specific screen genuinely belongs there.

The iOS router was left byte-identical to the peer branch `origin/monet/ios-order-cancel` it was
copied from, so that add/add merge still auto-resolves.  Bare `/console` remains unroutable by
design; the contract test below is what stops a future event type from quietly emitting it again.

### 3.2 An unrelated env var could break push routing by accident

**The mismatch.**  `pushLinkOrigin()` read `PUSH_DEEP_LINK_ORIGIN ?? NEXT_PUBLIC_APP_ORIGIN ??
"https://socratictrade.com"`.  `DeepLink.universalLinkHost` is an **exact** string match on
`socratictrade.com` — `www.`, any subdomain, or `http` all mean no routing at all.  Nothing else in
the repo reads `NEXT_PUBLIC_APP_ORIGIN`, so it was a live tripwire: someone setting that variable
for any other purpose would silently turn every push tap into a no-op while the web links kept
looking fine.

**The fix.**  Dropped the `NEXT_PUBLIC_APP_ORIGIN` inheritance.  `PUSH_DEEP_LINK_ORIGIN` remains as
the single deliberate override, with the host constraint documented at the function.

### 3.3 What was verified as already correct (not changed)

* **Register body** — iOS `PushRegistrationRequest.jsonBody` produces `{token, environment}` plus
  `bundleId` when known; the route accepts exactly that, defaults `platform` to `"ios"`, and
  rejects a `bundleId` that is not this server's APNs topic.  Lowercase hex from
  `hexEncoded(_:)` passes `normalizeDeviceToken`'s `/^[0-9a-f]{64,200}$/`.
* **Environment literals** — `APNSEnvironment` is a `String` enum whose case names *are* the wire
  values, and `isApnsEnvironment` accepts exactly those two.
* **Auth** — the push coordinator builds its client from `MobileAPIClient.productionBaseURL`, the
  same origin (and therefore the same `HTTPCookieStorage.shared` session) the store uses.  A second
  hardcoded host here would have sent every registration out unauthenticated.
* **Payload key** — the server writes the link at the payload ROOT under `url`
  (`buildApnsPayload`), which is the first of `PushPayload.linkKeys`.
* **Sign-out** — iOS `DELETE`s with `{token}` before `clearLocalSession()` clears the cookies; the
  route is owner-scoped, so one account can never unregister another's device.

### 3.4 Adversarial review pass (2026-08-12, second reviewer) — two defects found and fixed

**A. The Settings -> Delivery off-switch for iPhone push could not be turned off.**
`POST /api/mobile/push/register` re-added `"apns"` to the user's enabled channels on EVERY
registration, and the app re-registers on every launch (`registerIfAlreadyAuthorized`, correct and
required — APNs rotates tokens).  So a user who turned "iPhone push" off in Settings -> Delivery
had it switched back on the next time they opened the app, silently — contradicting the route's own
documented contract ("the user can still turn it off ... and turning it off is respected").
Fixed in `app/api/mobile/push/register/route.ts`: the channel is enabled only when the device is
NOT already a live row of this user's — i.e. a first registration, a reinstall, a shared phone
switching accounts, or a device coming back after sign-out / a 410 retirement (a disabled row is a
fresh opt-in).  A launch-time re-assertion of a live token leaves prefs untouched.  Two tests added
to `test/apns-register-route.test.ts` (off-switch holds across repeat registrations; a disabled row
re-enables).

**B. Cross-user notification window on a shared device after a session expiry.**
Token registration was attempted only in `bootstrap()`, only for a session already restored at cold
start.  Nothing registered after an in-session sign-in.  On the expiry path
(`clearLocalSession` -> `forgetTokenLocally`) no authenticated `DELETE` is possible and
`unregisterForRemoteNotifications()` is NOT called, so the server row stays live and owned by the
previous user and the APNs token stays valid.  If a DIFFERENT account then signed in on that phone,
the previous owner's alerts — titles and bodies carrying symbol/side — kept landing on it until the
next cold launch.  (The explicit sign-out path was already covered: it deletes the row and
unregisters from APNs.)  Fixed in `ios/SocraticTrade/MobileStore.swift`: `loginWithApple` and
`loginWithWebAuthCode` now call `claimPushTokenForCurrentSession()` after a successful sign-in,
which re-asserts the existing grant (never prompts) so the server reassigns the row to the new
session immediately.  Same change is also what gets push working on a FIRST sign-in without making
the owner relaunch the app.

## Appendix A — server half (folded from `2026-08-12-apns-push-server.md`)

Push is **not** a parallel notification pipeline.  It is one more `NotifyChannelId` in
`src/lib/notify.ts`'s `CHANNELS` record, reached through the same `sendNotification` -> `notify`
path as every other channel and gated by the same `policy.notificationSettings.enabledEvents`.  No
second `enabledEvents`-like concept was added.

```
sendNotification (notifications.ts)   <- existing per-event gate + repeat-dedup
  └─ notify (notify.ts)               <- existing per-user channel fan-out (notification_prefs)
       └─ CHANNELS.apns               <- the new channel
            ├─ listActiveDeviceTokens(userId)      (db-device-tokens.ts)
            ├─ pushDeepLink / pushCollapseId       (push-deep-links.ts)
            └─ sendApnsPush per device             (apns.ts, node:http2 + ES256 JWT)
```

The `apns` channel differs from the others in exactly one way: its target is app-managed (device
tokens the app registered) rather than a string the user types.  Two general extensions rather than
a special case: `ChannelDef.resolveTarget?({ userId, prefs })` (returns the live device COUNT —
never a token, because that value flows into result bookkeeping; `""` means "no target", which the
existing loop already reports as `skipped: "no_target"`), and `ChannelSendContext.userId`.

**Files:** `src/lib/types.ts` (`NotifyChannelId` gains `"apns"`; `ApnsEnvironment`, `DeviceToken`,
`NotifyChannelDescriptor.managedTarget?`) · `src/lib/db.ts` (migration **75 `device_push_tokens`**)
· `src/lib/db-device-tokens.ts` (new) · `src/lib/apns.ts` (new) · `src/lib/push-deep-links.ts` (new)
· `src/lib/notify.ts` · `src/lib/notifications.ts` · `src/lib/db-api-keys.ts` ·
`src/lib/account-deletion.ts` · `app/api/mobile/push/register/route.ts` (new) ·
`app/console/settings/delivery.tsx` + `lib.ts` · `next.config.mjs` · `test/apns-push.test.ts` +
`test/apns-register-route.test.ts` (new) · `test/persistence-hardening.test.ts` (74 -> 75).

**Registration contract**

```
POST /api/mobile/push/register
  auth: session (x-authenticated-user-email, set by middleware — never the body)
  body: { token: string, environment: "sandbox" | "production", bundleId?: string }
  200:  { ok: true, device: { token: "<masked>", environment, bundleId, platform, createdAt, lastSeenAt } }
  400:  malformed token / bad environment / bundleId != this server's APNs topic

DELETE /api/mobile/push/register
  body: { token: string }
  200:  { ok: true, removed: boolean }
```

Idempotent (re-POST refreshes, no duplicate row, original `createdAt` kept).  Registering adds
`"apns"` to `notification_prefs.channels` — allowing notifications on the device IS the opt-in — and
the last DELETE removes it.  Rate-limited 30/min.  The raw token is never echoed, logged, or
audited; only `maskDeviceToken` form.

**Decisions**

* **Token reassignment, not multi-owner.**  `device_push_tokens.token` is the PRIMARY KEY and
  registration reassigns on conflict.  Apple hands the same token to the same install regardless of
  who is signed in, so an "insert a second row" model would keep delivering the previous user's
  alerts to a shared phone.  Tested at registry and route level.
* **Environment stored, never inferred.**  Endpoint selection reads the token row, not `NODE_ENV`.
  TestFlight is PRODUCTION; assuming otherwise is `400 BadDeviceToken` forever, silently.
* **Dead tokens disabled, not deleted** — the row keeps `disabled_at` + `disabled_reason`, is never
  sent to again, and re-registering re-enables it (reinstall / re-granted permission).
* **JWT cached at 50 minutes.**  Apple requires >= 20 minutes of reuse and expiry at 60; minting per
  send earns `429 TooManyProviderTokenUpdates`.  `403 ExpiredProviderToken` invalidates the cache.
* **`node:http2`, never fetch** — APNs is HTTP/2-only and Node's global fetch/undici does not speak
  HTTP/2 to it.  One short-lived session per request: volume is a handful of alerts per user per
  day, so pooling buys nothing while a cached half-open session is a real source of stuck sends.
* **Bare `crypto`/`http2` specifiers.**  `src/lib/apns.ts` is reachable from the `src/lib/db.ts`
  barrel, which Next compiles into client/edge bundles.  A `node:`-scheme request is handled by
  webpack's scheme plugin BEFORE `resolve.alias`, so the existing `"node:crypto": false` alias
  cannot neutralize it — the build fails `UnhandledSchemeError`.  Bare specifiers go through
  `resolve.fallback`, hence `http2: false` in `next.config.mjs`.  (Several `"node:*": false` alias
  entries already in that config are probably dead for the same reason.)
* **Collapse ids on the noisy repeats only:** `approval-<SYM>-<side>`, `run-failed-<SYM>`,
  `kill-switch`, `price-alert-<alertId>`, `limit-stale-<SYM>`.  `fill` deliberately has NONE — two
  fills are two events and neither may replace the other on the lock screen.
* **Secrets by name from `process.env`** (`APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`,
  `APNS_PRIVATE_KEY_B64`) — the seam `RESEND_API_KEY` / `TWILIO_*` already use.  Nothing was
  created, rotated, read, or printed; tests generate a throwaway P-256 key at runtime.  A missing
  credential makes `loadApnsConfig` return `null` and the channel report
  `skipped: "not_configured"` — it never throws.

**Fail-soft posture.**  A push failure cannot break the trading path that triggered it:
`sendApnsPush` returns a result for every outcome including transport throws (it does not reject);
`notify()` catches per-channel failures and continues; `sendNotification` wraps the whole bridge.
`resolveTarget` is wrapped too, so a registry hiccup degrades to "no target" rather than aborting
the loop for the other channels.

## Appendix B — iOS half (folded from `2026-08-12-apns-push-ios.md`)

**Files:** `SocraticTrade.entitlements` + `project.yml` (`aps-environment: production` in BOTH) ·
`PushNotifications.swift` (new) · `DeepLink.swift` (new here, verbatim from the peer branch) ·
`MobileAPIClient.swift` · `SocraticTradeApp.swift` · `MobileControlView.swift` ·
`ProposalsView.swift` · `HomeView.swift` · `MobileStore.swift` · `PushNotificationTests.swift` +
`DeepLinkTests.swift` · `project.pbxproj`.

* **Entitlement is `production`, in both files.**  xcodegen REWRITES `.entitlements` from
  `project.yml` on every `generate`, so an entitlement added to only one is silently dropped by the
  next regen.  `production` is right because TestFlight and the App Store are the same APNs
  endpoint and a TestFlight build is a Release build re-signed by Apple with a *distribution*
  profile.  Verified empirically, not assumed: after the change the built bundle's
  `embedded.mobileprovision` reads `aps-environment = development` (automatic signing substituting
  for a local build) while the checked-in file says `production` — which also proves the App ID's
  push capability is live.
* **Environment read from the signature, never `#if DEBUG`.**  `APNSEnvironment.current` locates the
  XML plist inside the CMS-wrapped `embedded.mobileprovision` and reads
  `Entitlements.aps-environment`.  `#if DEBUG` describes optimization, not signing: a Release build
  run from Xcode with a dev profile gets *sandbox* tokens.  Unreadable profile on a real device
  resolves to `production` (a shipped install is the only realistic cause, and guessing sandbox
  recreates the exact silent failure); simulator always `sandbox`.
* **Permission on first visit to Proposals while signed in** — the screen whose purpose is "things
  are waiting for your judgment".  Never at cold start.  Account & Settings carries a manual "Turn
  On Alerts", so the trigger is a convenience, not a gate.
* **Foreground presentation is conditional on the SSE stream:** banner and sound suppressed only
  while the stream is connected (the screen already shows the event); still delivered to
  Notification Center and the badge.  When the stream is DOWN the banner IS shown — a flat
  suppression would hide real news precisely when the app has stopped receiving it.
* **One router, from an unlanded branch.**  `DeepLink` and its tests were copied byte-identical from
  `origin/monet/ios-order-cancel` (not on `main`) so an add/add merge auto-resolves, and push taps
  route through `DeepLink.destination(for:)` into the same `pendingDeepLink` slot `onOpenURL` fills.
  The peer's proposal-focus ring was NOT copied (it depends on their `ProposalsView`).
* **Sign-out withdraws the token BEFORE cookies are cleared** — a delete after `clearLocalSession()`
  arrives unauthenticated — and also calls `unregisterForRemoteNotifications()`, so a failed delete
  still ends in the server's `410 Unregistered` cleanup.  The expired-session path cannot make an
  authenticated call, so it only drops the local belief.
* **Honest state.**  `PushAlertState.isWorking` is true only for a completed server registration.
  Denied permission, an APNs failure, and a rejected token each surface verbatim in Account &
  Settings with the real reason and the right next step.  The app never implies alerts are arriving
  when they are not.

### 10.2 The one conflict that was a real bug, not a formatting choice

Section 8 of this note recorded that `DeepLink` was copied byte-identical from the unlanded
`monet/ios-order-cancel` branch, and that "the peer's proposal-focus ring was NOT copied (it
