# 2026-06-22 — Phase-11 M6: Real Identity/Auth (Auth.js v5 + CF Access)

## Summary

Implements Phase-11 M6: real identity via Cloudflare Access + Auth.js v5 Google
sign-in, with a reliable fail-closed arming signal that closes the NODE_ENV-edge-inlining IDOR.

### Critical bug fixed

`middleware.ts` previously failed closed only when `process.env.NODE_ENV ===
"production"`. However, Next.js **inlines `NODE_ENV` at build time** in the edge
runtime — so at runtime in the live deployment `isProd` is `false` and **every
request fails open** to `PRIMARY_EMAIL ("local")`. A direct request with no
identity header returned 200.

### New fail-closed signal

```ts
authConfigured = (CF_ACCESS_TRUST_EMAIL_HEADER === "1") || !!AUTH_SECRET
```

This is evaluated at **request time from actual env vars**, not from an
inlined build constant. When either is set, unauthenticated requests fail
closed (401 for `/api/*`, redirect to `/login` for pages). When neither is
set (local dev, tests) the `PRIMARY_USER_EMAIL` fallback applies — no behavior
change.

### Identity source resolution (first match wins)

1. Cloudflare Access `cf-access-authenticated-user-email` header — trusted only when
   `CF_ACCESS_TRUST_EMAIL_HEADER=1`.
2. Auth.js v5 session JWT cookie (`authjs.session-token` / `__Secure-authjs.session-token`)
   — decoded with Auth.js' edge-safe JWT helper using `AUTH_SECRET`.
3. `PRIMARY_USER_EMAIL` fallback — only when `authConfigured=false`.

## Why

The previous `isProd` gate was unreliable in the edge runtime. Once the owner
sets `CF_ACCESS_TRUST_EMAIL_HEADER=1` (CF Access active) or `AUTH_SECRET`
(Google sign-in active), the IDOR is closed immediately — no code change needed
for activation.

## Edge approach chosen: Auth.js JWT decoder

The first M6 branch used `jose/jwt/verify`, but that subpath is not exported by
the installed `jose` package and caused a Next.js module-not-found build error.
The middleware now keeps the import narrow:

- `middleware.ts` imports only `src/lib/auth/session-edge.ts`
- Auth.js is configured with the shared `encodeSessionToken`/`decodeSessionToken`
  helper, so it writes compact HS256 session JWTs that middleware verifies through
  narrow `jose/jwt/sign` and `jose/jwt/verify` subpath imports.
- `src/lib/auth/auth.ts` uses next-auth normally for the server-side config,
  `handlers` (route), and the `auth()` helper for server components.

## Owner activation steps

### To activate Cloudflare Access path (no code change needed)

1. Ensure the app is behind a Cloudflare Access application with email policy.
2. Set `CF_ACCESS_TRUST_EMAIL_HEADER=1` in `.env.local` (or deployment env).
3. That's it — middleware immediately fails closed and trusts the CF header.

### To activate Auth.js v5 Google sign-in

**Step 1 — Google Cloud Console**

1. Go to https://console.cloud.google.com → APIs & Services → Credentials.
2. Create credentials → OAuth 2.0 Client ID.
   - Application type: **Web application**
   - Authorized JavaScript origins: `https://<your-domain>` (e.g. `https://socratictrade.com`)
   - Authorized redirect URIs: `https://<your-domain>/api/auth/callback/google`
3. Copy the **Client ID** and **Client Secret**.
4. Under OAuth consent screen → add your email as a test user (if in testing mode).

**Step 2 — Environment variables**

Copy `.env.example` → `.env.local` and fill in:

```bash
# Generate a stable signing secret:
AUTH_SECRET=$(openssl rand -base64 32)

AUTH_GOOGLE_ID=<your-client-id>.apps.googleusercontent.com
AUTH_GOOGLE_SECRET=<your-client-secret>
```

**Step 3 — Deploy / restart**

The moment `AUTH_SECRET` is non-empty, the middleware arms (`authConfigured=true`) and
all unauthenticated requests fail closed. First sign-in flows through `/login` → Google
OAuth → `/api/auth/callback/google` → back to `/`.

**Both paths can coexist**: CF Access (header) takes priority; Auth.js session is the
fallback for requests that don't carry the CF header (e.g. direct-to-origin access).

## Follow-ups / deferred

- Email allowlist enforcement is already in place (`ALLOWED_EMAILS` env var); the owner
  should populate it once multi-user access is needed.
- Per-user Robinhood account linking (noted in M6 scope) is separate work — the
  identity layer is now in place.
- The `access-denied` page now only covers the "authenticated but not allowed" case;
  the `/login` page covers "not authenticated". Both are in `PUBLIC_PREFIXES`.
- If Cloudflare Access is removed in the future, set `AUTH_SECRET` + Google creds to
  keep auth armed.
