# 2026-09-07 — Remove redundant postcss override (recurring Dependabot failure)

## Context & Objective

Every Dependabot Updates job touching `postcss` has failed since 2026-08-24 (recurred 08-24 x3, 08-25, 08-31, 09-07) with:

```
| postcss | dependency_file_not_resolvable | "Override for postcss@8.5.28 conflicts with direct dependency." |
```

Root cause: `package.json` pinned `postcss` identically in both the direct devDependency (`^8.5.15`) and the `overrides` block (`^8.5.15`).  Dependabot cannot bump one side of that pair without the other going stale, and flags the manifest as unresolvable rather than guessing which side to change.  Goal: stop the recurring failure without accidentally breaking a version pin something else depends on.

## Changes Made

- `package.json` — removed the redundant `"postcss": "^8.5.15"` entry from `overrides` (kept `overrides.axios` untouched).
- `package-lock.json` — regenerated by `npm install` to reflect the new resolution.
- `STATUS.md` — snapshot entry for this fix.
- `PLAN.md` — one-line scope note.
- `docs/EFFORT-LOG.md` — cross-agent ledger row.
- `docs/rollouts/2026-09-07-postcss-override-conflict.md` — this note.

## Decisions & Trade-offs

Checked whether the override was load-bearing before removing it.  **Correction from an earlier revision of this note:** the initial claim that "`next` resolves its own nested postcss copy independent of the override" was wrong, and Codex correctly caught it.  The actual pre-change lockfile (`origin/main` at `14eabced9`) had exactly ONE `postcss` entry in the whole tree — the deduped root `node_modules/postcss@8.5.15` — with no nested copy anywhere, including under `next`.  npm's top-level `overrides` field is transitive by design: it forces every package in the tree named `postcss` to resolve to the override's range, overriding what each dependent itself declares, unless you scope the override key (e.g. `"next>postcss"`).  So the override was in fact forcing `next` (which declares an exact `postcss: 8.5.23` dependency in its own `package.json`) down to the shared `8.5.15` — a real, active effect, not a no-op for `next`.

What the override was *not* doing is forcing anyone to something OLDER than what they wanted for a compatibility reason:

- `@tailwindcss/postcss@4.3.3` declares `postcss: ^8.5.16` — newer than the override's `8.5.15`, so the override was holding it back one version below its own stated minimum.
- `vite@8.2.2` (vitest's dependency) declares `postcss: ^8.5.26` — also newer than the override.
- `next@16.3.4` declares `postcss: 8.5.23` (exact) — the override was forcing it four patch versions below what it actually ships and tests against upstream.

Removing the override lets npm's normal resolution run: the direct devDependency (`^8.5.15`) plus `@tailwindcss/postcss` (`^8.5.16`) and `vite` (`^8.5.26`) all dedupe to a single hoisted `postcss@8.5.28`, and `next`'s exact `8.5.23` pin — now free of the forced override — gets its own nested `node_modules/next/node_modules/postcss@8.5.23` copy, matching what Next.js itself declares and presumably tested against.  Net effect: this is a **behavior change for `next`'s bundled PostCSS version** (8.5.15 → its own intended 8.5.23), not the no-op the earlier revision of this note claimed.  It is very likely a correctness improvement — Next was previously running against a PostCSS version four patches older than the one it actually depends on — but it is a real change, verified by a full production-config `npm run build` (Tailwind/PostCSS pipeline exercised end-to-end, output generated normally, no errors) and the repo's CI `verify-hosted` gate (see Verification State) rather than assumed safe.  No edge cases are being deliberately ignored.
