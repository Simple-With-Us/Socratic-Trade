# 2026-06-21 — Pattern-Day-Trader (PDT) gate

## Summary

Added a Pattern-Day-Trader (FINRA Rule 4210) gate to policy enforcement. A LIVE
(real-capital brokerage) account holding less than $25,000 of equity is now
blocked from placing an OPENING order (buy/short) that would enable a 4th
day-trade within a rolling 5-business-day window.

- `src/lib/db.ts`: new `countDayTradesInLastBusinessDays(accountNumber, businessDays, asOf, userId, timeZone)`.
  Reads `fill_events`, buckets fills by `symbol` + market-calendar day
  (America/New_York, the same boundary used by the daily-notional reset), and
  counts a day-trade for any bucket that has BOTH an opening fill (`buy`|`short`)
  AND a closing fill (`sell`|`cover`) on that day. Sums distinct qualifying
  buckets over the last N business days (weekends skipped) ending at `asOf`,
  inclusive. Account scoping uses the existing `scopeAccount()` helper, mirroring
  `dailyExecutionStats` / `notionalInLastMinutes`.
- `src/lib/policy.ts`: new `PolicyContext` fields `isLiveExecution?: boolean` and
  `priorDayTradeCount?: number` (threaded in like the other precomputed counts),
  plus exported constants `PDT_EQUITY_THRESHOLD` (25_000) and `PDT_MAX_DAY_TRADES`
  (3). The gate fires only when `isLiveExecution === true`, the proposal is an
  opening order (`buy`|`short`), `portfolio.totalMarketValue < 25_000`, and
  `priorDayTradeCount >= 3`; it pushes a `pdt_rule: ...` rejection reason. Closing
  orders (sell/cover) are never blocked.
- `src/lib/strategy.ts`: both `evaluateTradeProposal` call sites (the run loop in
  `runStrategyOnce` and the approval path in `executeProposal`) now pass
  `isLiveExecution` and `priorDayTradeCount`. The day-trade count query is only
  executed for LIVE execution; Test/local and broker-Paper pass `0`.

## Why

Owner-resolved regulatory decisions (implemented exactly, not re-litigated):
day-trade = same-symbol round-trip CLOSED on the same calendar day; lookback =
rolling 5 business days; equity source = `Portfolio.totalMarketValue`; threshold
= $25,000; action = BLOCK; scope = LIVE/brokerage execution ONLY (Test/local
simulation and broker-Paper accounts cannot violate PDT and are never gated).

Scope determination reuses the existing execution-state signal: the run loop's
`learningSource === "live"` and `executeProposal`'s
`!executionState.usesLocalSimulation && executionState.environment === "live"`
both identify the broker/live (real-capital) state; Test and broker-Paper map to
non-live. No new live/paper plumbing was invented.

New tests (`test/pdt.test.ts`) cover:
- `countDayTradesInLastBusinessDays`: counts same-day buy→sell and short→cover
  round-trips per symbol+day; excludes orphan legs and cross-day legs; respects
  the rolling 5-business-day window edge (a Fri-before-window round-trip is
  excluded).
- PDT gate: opening LIVE order with equity < $25k and 3 prior day-trades is
  BLOCKED (`pdt_rule`); equity >= $25k is NOT blocked; a paper/Test account
  (non-live) is NOT blocked regardless of equity/count; < 3 prior day-trades is
  NOT blocked; a closing (sell) order is never falsely blocked; an opening short
  is blocked the same as a buy.

## Follow-ups

- The PDT block fires only when the count is threaded into the policy context. The
  two production call sites in `strategy.ts` are wired; any future caller that
  constructs a `PolicyContext` for a LIVE account should pass
  `isLiveExecution`/`priorDayTradeCount` to enforce the gate.
- Day-trade detection counts at most one day-trade per symbol per day (the
  regulatory definition for this purpose); partial-fill / multi-round-trip nuance
  per symbol-day is intentionally not modeled.
