## PR #2 — DestinationTab mapping layer + one-time localStorage shim

**Flag:** `NAV_V2` (env `NEXT_PUBLIC_NAV_V2` + `localStorage` override `nav-v2`). The shim itself is
**flag-independent** by design.

### Summary
Introduced the destination vocabulary as a *mapping* over today's `WorkspaceTab`/`FeedTab` values and a
one-time migration of every returning user's localStorage, so later PRs can re-point a destination's panel
without a second migration. **Panels do not move; rendering is byte-identical with the flag on or off.**

- New pure module **`app/nav-destinations.ts`** (single source of truth, unit-tested):
  - Moved `WorkspaceTab`/`FeedTab` types + `isWorkspaceTab`/`isFeedTab` guards + `WORKSPACE_TAB_KEY`/
    `FEED_TAB_KEY` out of `dashboard-client.tsx` (values unchanged).
  - New `DestinationTab` (`dashboard·approvals·scan·strategy·guardrails·results`) + `FeedDestination`
    (`activity·runs·alert-history·audit`) unions and guards.
  - Forward maps: `decision/macro/assistant→dashboard`, `market→scan`, `performance/tax→results`,
    `strategy→strategy`; feed `notifications→alert-history`. Reverse `destinationToWorkspaceTab` gives the
    canonical current panel for each destination (approvals/guardrails resolve to the nearest existing
    panel so the renderer never has a gap).
  - `isNavV2Enabled(storage)` — `localStorage` override wins, else `NEXT_PUBLIC_NAV_V2` env, else off.
  - `migrateNavKeysToDestinations(storage)` — **additive-write, idempotent, per-key** shim: writes a
    destination key only when it is absent and the legacy key is valid; legacy keys are left intact (a
    flag-off render path still reads them; their deletion is a later cleanup PR).
- `app/dashboard-client.tsx`: import the above; run the shim once on mount (flag-independent); no render
  or persistence behavior change (legacy keys still drive the tabs this release).
- Test **`test/destination-shim.test.ts`** (12 cases): mapping totality + the `notifications→alert-history`
  rename, 1:1 destination round-trip + many→one canonical resolution, shim seed/idempotency/partial-state/
  first-run/garbage-value, legacy guard aliases, and the flag override-vs-env precedence.

### Do-not-break checklist
All N/A except: no execution/scope/data path touched; flag-off render is byte-identical; the shim is
additive (legacy keys retained), so rollback is a flag flip and a flag-off user is never stranded.

### Verification
`tsc` clean · `lint` 0 errors · `npm test` 197 files / 1993 tests (+1 file / +12) · `build` success.

low-risk scope-first framing, without a risky teardown of the ~1000-line inline settings modal (the full
physical re-nest of the 8-node Scope B tree + the live Essentials/Advanced re-render land with the shell in

- New pure module **`app/settings-search.ts`** — one catalog (`SETTINGS_FIELDS`) that is the single source

  (`scopeMatchesLegacyTier` cross-checks each field against `settingsTierForSection`, the tier SSOT).
  - **Gap #4 resolved:** the Essentials `Max order size (per trade)` binds to `maxOrderNotional` and never

- `app/dashboard-client.tsx`: **Scope-A signpost + governing-rule divider** (copy deck §7.10) shown in the
  user-tier Settings when `NAV_V2` is on — "if it changes how a trade is decided or placed → account",
  with `Open Strategy ›` / `Open Guardrails ›` jumps. Flag-off modal is byte-identical.
- Tests: `settings-search-index.test.ts` (index derived from catalog + old-name synonym redirects),
  `guardrails-essentials.test.ts` (exactly 5, correct bindings, `maxOrderNotional` sole backing, no
  "position"), `settings-tree-scope.test.ts` (scope vs legacy tier consistency, unique ids).
