# ST-4605: iOS app lock

## Context & Objective

ST-4605 splits the optional iOS app lock out of ST-4596.  The Keychain session-cookie work stays on PR #5131.  App lock does not call that code, so this branch is based on current main.

## Changes Made

Optional device gate, off by default.  Face ID, Touch ID, or the device passcode is required after launch and after the app has been in the background for more than one minute.  If the device cannot authenticate, the setting cannot be turned on, and a lock that is already on offers Turn Off App Lock instead of trapping the user.

## Decisions & Trade-offs

- Based on `main`, not `gb-engineer/st-4596-ios-keychain-app-lock`. No `SessionKeychain`, cookie jar, or `MobileStore` persistence changes.
- The timeout is a fixed 60 second grace, not a picker.  Returning inside the window clears the background timestamp so a later render does not lock the app while it is still in the foreground.
- The policy is `LAContext.deviceOwnerAuthentication`, so the system falls back to the device passcode.  `localizedFallbackTitle` stays unset so a custom button does not replace that passcode UI.
- The lock screen is its own window, above the app window and below system alerts.  A root full-screen cover cannot present while a sheet is already up, so account settings and trade sheets stayed visible.  The sheet stays underneath and is covered until unlock.
- Device-auth availability is injected in tests so XCTest does not depend on simulator enrollment.
- Foreground resume reloads the snapshot and starts the live stream when it is not already connected.  Backgrounding marks the scene as not active, stops the stream, and invalidates that resume so it does not start the stream again when the reload finishes.
- A canceled first load can leave the session initialized and signed out.  The next unlock loads again instead of treating that as a live resume.
- Overlapping unlock and scene-active resumes share one in-flight reload.  Waiters suspend on a continuation, so cancelling one caller does not cancel that reload.  A waiter that did not get a live stream runs one fresh resume and does not rejoin the finished one.
- A connected stream is left up across that reload.  `startEvents` replaces its previous task, so calling it again on the way back from Control Center would drop the open connection.
- Unlocking a finished signed-out session does not fetch the snapshot.  Only a first load that was cancelled before sign-in is fetched again.
- Returning to the foreground while the lock screen is up prompts again.  Cancel does not, because that attempt is cleared only when the app actually backgrounds.
- While Require App Lock is on, the cover is up whenever the scene is not active, so the app-switcher snapshot is blank.  The Face ID prompt still waits until the one-minute grace has elapsed.  The app window is retained strongly and restored when the cover dismisses.
