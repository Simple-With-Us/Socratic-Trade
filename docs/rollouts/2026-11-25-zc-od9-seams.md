## 3. Decisions & Trade-offs

- **Defaults are ON inside propose authority, with explicit OFF overrides.**  `tuning.chatHardConstraintsInPropose` (undefined = include) and `tuning.acceptedFrameworkProposalsToOverlays` (undefined = emit) are the owner-adjustable preferences the OD-9 ruling asked for; false disables each seam.  Users with no hard memory rows get a byte-identical prompt, and accounts with no accepted proposals get no overlay rows.
- **Propose mode only.**  Both gates require `policy.strategyAuthority === "propose"`.  In "decide" (autonomous) authority the seams are deliberately inert — the machine never acts on chat-memory-derived content without the human approval rail, matching "land in propose mode only".
- **Never a silent cage.**  Hard constraints are prompt DATA that never mutate caps, gates, sizing, or placement; approving a proposal that conflicts with one is the explicit owner override.  Emitted overlays ride the existing containment seam (same trust tier as `ownerCoaching`, still under `strategyOverlaysEnabled` + `maxActiveOverlays`).
- **Overlay emission over learned_context.**  The Linear description allowed "strategy_overlays or learned_context".  Overlays were chosen because that is the existing documented containment seam with an `appliedOverlayIds` receipt and the right trust tier; `learned_context` rows carry tiered approval/ownership semantics better suited to decision-derived facts.
- **Dedupe mechanics.**  The veto counterfactual keeps the existing `INSERT OR IGNORE` deterministic id in `skipped_candidate_counterfactuals`; the new decision row uses its own derived id and the outcome-engine's `getSkippedCounterfactualByRunSymbol` join — one measurement, two receipts, nothing double-booked.
- **Deferred (OD-8, awaiting the ST-4678 lift scorecard):** D5d adversarial Red query, D6a hypothesis grading, D6c candidate-pool flag.  Not implemented, per the roadmap batch plan.

## 7. Kody review #5488 fixes (same lane, 2026-11-25)

Kody review on PR #5488 returned five findings; each is fixed in this lane commit.

1. **Race on overlay id (68IGBb).**  `createStrategyOverlay`'s find-then-insert became a single atomic `upsertStrategyOverlay` (`ON CONFLICT(id) DO UPDATE` writes name/regimes/instructions/priority/enabled/updated_at) in `src/lib/db-overlays.ts`; the applier calls it directly, so concurrent accepts of one framework id conflict-merge instead of throwing.  The framework PATCH route additionally wraps the applier in try/catch and audits `socratic_framework_overlay_emission_failed`, so a saved acceptance can never fail the request.
2. **Model-authored instructions (68IGGD, security).**  Instructions now carry ONLY the owner's confirmed text: `applyAcceptedFrameworkProposal` requires a non-empty `ownerResponse` (skip reason `owner_text_required` otherwise), so a plain accept without owner text never persists the LLM's `proposedChange` as an enabled instruction.  The confirmed text is control-character-stripped, whitespace-collapsed, capped at 800 chars, and containment-quarantined (`containPromptText`, "coach" source) before the upsert.  Caller check: the PATCH route validates `ownerVerb`/`ownerResponse` only for the rewrite verb (rewrite requires ownerResponse); no caller validated a plain accept's response before this change.
3. **Stale priority on re-accept (68IGLB).**  Fixed by the same upsert: `priority` is computed from the FRAMEWORK_PRIORITY mapping on every emission, so a re-accept refreshes it instead of keeping the first-accept value (drop of findings 1 and 3 rides one mechanism).
4. **Full-memory scan in the hot path (68IGQZ, perf).**  New `listHardLiveMemory` in `src/lib/db-api-keys.ts` pushes the hard filter, the per-subject newest-row dedupe (`rowid IN (SELECT MAX(rowid) … GROUP BY subject)`), the ORDER BY and the LIMIT into one SQL query; `listHardMemoryConstraints` is now a thin wrapper, so proposeTrades cost no longer grows with the memory history.
5. **Veto key collision (68IGUE, HIGH).**  `redVetoDecisionId` is now `red-veto:<runId>:<symbol>:<fingerprint>` with a SHA-256-12 proposal fingerprint over (side | thesis tag | dollar amount | reference price).  A second veto of a different proposal for the same symbol gets its own ledger row; a re-veto of the same proposal shape still UPSERTs one row and preserves a matured outcome.

## 8. Kody review #5488 second pass (same lane, 2026-11-27)

Three follow-up findings on the pushed fixes; each fixed in this lane commit.

1. **Memory dedupe revision order (68LooK, MEDIUM).**  `listHardLiveMemory`'s per-subject dedupe previously kept `MAX(rowid)`, which returns the wrong revision when insert order diverges from `asserted_at`, and it kept blank subjects.  The query now uses `ROW_NUMBER() OVER (PARTITION BY subject ORDER BY asserted_at DESC, rowid DESC)` with `TRIM(subject) <> ''`, so the newest-asserted revision wins and whitespace-only subjects never claim a cap slot.
2. **Cross-owner overlay upsert (68Loq4, SECURITY HIGH).**  `ON CONFLICT(id)` targets the global PRIMARY KEY, so a colliding id could rewrite ANOTHER USER's overlay.  `upsertStrategyOverlay` now guards the DO UPDATE with `WHERE strategy_overlays.user_id = excluded.user_id` and checks `result.changes`: a foreign-owner collision writes nothing and throws `strategy_overlays id ... is owned by another user`, which the framework PATCH route's existing best-effort catch turns into an audit receipt, never a failed acceptance.
3. **Volatile veto fingerprint (68Lot-, MEDIUM).**  The proposal fingerprint hashed `dollarAmount`/`referencePrice`, so the same proposal vetoed twice with slightly different numbers duplicated ledger rows.  It now hashes only stable identity fields (side + deterministic thesis tag; `TradeProposal` carries no id), keeping same-shape re-vetoes as a single UPSERT.
