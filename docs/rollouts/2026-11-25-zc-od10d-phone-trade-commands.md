# [ZC:   RR.3.S] ST-4685 OD-10d phone trade commands: position.close, position.trim and order.replace_at_market

## 1. Context & Objective

Owner ruling OD-10d (Tue, Nov 24, 2026, about 11:26 PM CT) approved phone-side Close, Trim and Replace-at-Market actions for ST-4685 (child of the ST-4668 roadmap), with one hard boundary: the commands must run through the EXISTING order path with the same confirmation ceremony the web approval card already enforces, and nothing may widen the tradable universe.  This change is server-side only; the iOS row actions are the documented follow-up.

## 2. Changes Made

All command logic was added to the mobile command gateway; every placement, cancel, confirmation and replacement primitive is a REUSED export from the existing rails.  No owner-merge file (src/lib/order-*.ts, src/lib/execution*, src/lib/db-execution.ts, src/lib/strategy-execution.ts, app/api/orders/, app/api/proposals/) was edited.

- `src/lib/mobile-api.ts`
  - `MOBILE_COMMAND_TYPES` gained `position.close`, `position.trim`, `order.replace_at_market`.
  - `normalizeCommandPayload` + new `normalizePositionExitPayload`: symbol validated against the equity universe (`isValidAppSymbol`), `fraction` bounded to (0, 1], `quantity` > 0, the two mutually exclusive, `position.trim` requires one, optional `accountNumber` (the expectedAccountNumber staleness pointer, same as `order.cancel`), optional `proposalId` retry pointer and pass-through `liveConfirmation`.
  - New `runPositionExit(command, trim)`: resolves the live account via `getActiveConnectedAccount` + `deriveExecutionState`, reads the fresh broker positions through the policy gateway, sizes the exit from the held lots with `heldPositionFor` (SELL closes a long, COVER closes a short), rejects oversizes and zero-rounding trims, then stages a `proposed` market-order card via `insertProposal` (deterministic `runId = mobile:<commandType>:<commandId>` plus `findProposalIdByRunId` so a re-run of the same command row reuses its card) and hands it to `executeProposal` — the exact rail the chat-draft bridge (`src/lib/chat/promote-draft.ts`, `app/api/proposals/from-draft/route.ts`) documents: insertProposal -> approve -> executeProposal.  Placement outcome classification reuses `resolvePlacementOutcome` / `PLACED_APPROVAL_STATUSES` / `ProposalNotPlacedError` unchanged.
  - New `order.replace_at_market` handler: the console's `POST /api/orders/replace-market` body verbatim — `withAccountMutation` (lane `manual-replace`, `LANE_WAITS.manualReplace`) around `replaceStaleLimitOrderWithMarket` from `src/lib/order-replacement.ts`, including its built-in live confirmation (`MarketReplaceConfirmation`, phrase `REPLACE LIVE <SYMBOL>`) and precondition errors.  Nothing was reimplemented; success-path coverage for the replacement engine itself already lives in `test/order-replacement.test.ts` and `test/route-orders-replace.test.ts`.
  - Classification: `order.replace_at_market` joins `IMMEDIATE_MOBILE_COMMAND_TYPES` (same seat as `order.cancel`: immediate, NOT protective). `position.close`/`position.trim` are deliberately queued, sharing `proposal.approve`'s rail and its strategy lock.
  - New `PositionExitStagedError` + `errorPayload` branches: on a live account whose policy requires typed confirmation, the first attempt stages the card and fails with `{ error: "LIVE_CONFIRMATION_REQUIRED", proposalId, staged: true, reasons, expectedText }` — the same machine-readable shape as the existing `LiveApprovalConfirmationError` branch, plus the card id, so one client prompt serves both and the unchanged `proposal.approve` ceremony is the fallback path. `MarketReplaceConfirmationError` and `MarketReplacePreconditionError` map to the analogous structured results.
  - `redactPayloadForResponse` now strips `liveConfirmation` (the typed phrase) from every response for `position.close`, `position.trim` and `order.replace_at_market` (already the behavior pattern of `proposal.approve`).
  - `staleMobileCommandStillAlive` grants the crash-sweep the same liveness grace to `position.close`/`position.trim` that `proposal.approve` has: a staged card (looked up by the command-keyed runId) that moved past `proposed`, or that emitted recent proposal receipts, is slow-not-dead; declaring a live money-path command dead invites a duplicate order.
- `test/mobile-trade-commands.test.ts` (new): 17 tests against a temp SQLite DB with a mocked BrokerGateway keyed by account (TestBrokerGateway-class test infrastructure only; no LLM, no live broker, no network).  Paper close queued->succeeded on the real executeProposal rail (and COVER for a held short), fractioned trim, queue-time validation (oversize fraction, fraction+quantity collision, trim-without-size), live-mode typed-confirmation refusal + staged card + confirmed second attempt reusing the same card (one proposal row total), cross-user proposalId pointer refusal, expectedAccountNumber staleness refusal for close and replace, idempotent replay returning the first command with a single placement, per-user scoping (a stranger's close never touches the holder's book), replace e2e through the replacement state machine (cancel settles, 8 of 10 shares re-placed at market) plus unknown-order precondition refusal and non-protective blast radius (a queued `strategy.run_once` survives).
- `STATUS.md`: top stanza for ST-4685.

## 3. Decisions & Trade-offs

- REPLACE-AT-MARKET WAS NOT SKIPPED: a reusable exported replacement seam exists (`replaceStaleLimitOrderWithMarket` in `src/lib/order-replacement.ts`, already carrying its own typed-confirmation ceremony `assertMarketReplaceConfirmation` and precondition errors), so the command is a thin dispatcher mirroring the web route rather than a second implementation.  It therefore also inherits the engine's scope: only stale WORKING limit/stop-limit orders (per `listStaleLimitOrders`, threshold `policy.staleLimitOrderMinutes`) are replaceable — an arbitrary resting order is refused with `replace_precondition_failed`, which is the honest OD-10d reading ("Replace-at-Market" is the console feature, not a new cancel-and-chase-any-order lever).
- `order.replace_at_market` is immediate but NOT protective, mirroring the documented `order.cancel` reasoning: a phone replace is worth nothing if it queues behind a 30-minute run, and replacing ONE resting order must not cancel the operator's other queued work. `position.close`/`position.trim` are queued because they are placements through the approval rail; racing `proposal.approve` for the strategy lock outside the sequential worker would only convert one of the two into a "busy" failure.
- Live confirmation is honored, not bypassed, by REUSE: `executeProposal` runs `assertLiveApprovalConfirmation` with `requireTypedConfirmation: policy.requireTypedConfirmation !== false`, so an owner who turned typed confirmation off gets a one-tap close (the template guardrail: owner-adjustable, honest off-switch).  The staging-then-confirm shape exists because the typed phrase must cover a concrete proposal id and estimated notional, neither of which exists at first tap; the retry path accepts `proposalId` but only after server-side validation that the card is this user's, still `proposed`, phone-minted (`runId` prefix `mobile:position.`) and same-symbol — a pointer, never a capability.
- Exits are sized only from the broker's own position read (`heldPositionFor`), with `applyPositionInvariant` in the placement choke point still bounding the actual order; no notional/dollar close path was exposed to keep the phone surface quantity-honest.  Universe-widening: none — a close of a HELD symbol goes through the same exit gates the console approval path already allows for held positions; no new symbols become tradeable.
- `tradeThesisTag: "Manual-Phone"`, `entryMarketRegime: "Manual"` follow the chat-draft precedent (`"Manual-Chat"`), keeping learning-loop rows attributable to the phone lane.

## 5. Next Steps & Blockers

- iOS row actions (ST-4685 follow-up): Close/Trim/Replace buttons on the position and working-order rows, calling `POST /api/mobile/commands` with the payloads validated here; for live accounts, render the `expectedText`/`proposalId` from the `LIVE_CONFIRMATION_REQUIRED` result and re-send with `liveConfirmation` (or drive the existing `proposal.approve` for the staged card).

## 6. Zero-Code Findings

- The three mobile command types required NO changes to `src/lib/order-*.ts`, `src/lib/execution*`, `src/lib/db-execution.ts`, `src/lib/strategy-execution.ts` or any `app/api/orders|proposals/` route: every needed primitive (`executeProposal`, `assertLiveApprovalConfirmation` via it, `insertProposal`, `findProposalIdByRunId`, `getActiveConnectedAccount`, `heldPositionFor`, `replaceStaleLimitOrderWithMarket`, `withAccountMutation`, `resolvePlacementOutcome`) was already exported.  No missing seam; nothing was skipped.
- The crash-sweep liveness proof for a phone exit cannot read the proposal id from the payload (it is minted at execution), which is why the staged card is keyed to the COMMAND id via a deterministic runId — that key doubles as the re-entry guard for retried command rows.
