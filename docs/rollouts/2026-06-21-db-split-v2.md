# 2026-06-21 — refactor(db): split db.ts into 8 focused modules (v2, re-derived from main)

## Summary

`src/lib/db.ts` grew to 2,964 lines after the stale PR #46 was superseded by ~290 lines of new
persistence functions merged onto main (learned-context, RAG ingestion, per-user scoping,
`migrateGlobalPolicyToLocalUser`, `findInternalSettingByKeyLike`, `deleteStrategyProfile`).

This refactor re-derives the split from current main. `db.ts` is reduced to a 586-line core
(schema/migration, `getDb()`, `audit()`, and re-export barrel); every function was extracted
into one of 8 focused modules.

## Why

- `db.ts` at 2,964 lines is too large to reason about in a single context window.
- Pure mechanical extraction with zero behavior changes — safe to merge any time.
- PR #46 was stale; this supersedes it cleanly.

## Decisions

- `mergePolicy` and `normalizeScoringWeights` are duplicated between `db.ts` (for migration-time
  use, before all modules are loaded) and `db-profiles.ts` (for runtime callers). The local copy
  in `db.ts` is private; the one in `db-profiles.ts` is exported. This avoids a module-load-order
  issue where `migrate()` runs during `getDb()` before the module graph is fully initialized.
- `getPolicy()` in `db-profiles.ts` imports `getActiveConnectedAccount` from `db-api-keys.ts`
  directly (not via `db.ts`) to avoid a circular import at module initialization time.
- `scopeAccount` is exported from `db-execution.ts` (used by `db-proposals.ts`) — cross-module
  dependency is intentional and one-directional.
- Every existing `import ... from "./db"` (or variants) continues to resolve via the barrel
  re-exports — zero consumer changes required.
