### structured-decision-scorecard - PLANNED (deferred, board row exists)
**Validated per-symbol decision-dashboard schema with price levels, attribution weights, and a decision-chain state machine**

The repo forces the LLM's entire per-symbol verdict into one validated JSON 'Dashboard' contract instead of prose plus loose numeric fields: core_conclusion (one-sentence thesis + separate no-position/has-position advice), a data_perspective block (MA alignment, price/MA table, volume), battle_plan.sniper_points (ideal_buy / secondary_buy / stop_loss / take_profit as explicit numeric entry-exit levels), an action_checklist of pass/warn/fail precondition items, signal_attribution (technical/news/fundamentals/market weights auto-normalized to sum to 100 via a validator), and an agent_disagreement_explanation whose Literal-typed adjustment chain must be contiguous from starting action to final action (extra='forbid', and an 'override applied' flag requires a real from/to transition).  Socratic-Trade's TradeProposal has thesis tags and reasoning text but no equivalent renderable scorecard contract; adopting a zod-validated version would give every proposal a daily dashboard report, make red-team overrides auditable as chain steps, and make price levels machine-usable for alerts and grading instead of buried in prose.

External-repo evidence: src/schemas/report_schema.py (Dashboard pydantic schema: sniper_points, signal_attribution model_validator, AgentDisagreementExplanation chain validation); templates/report_markdown.j2 (renders each dashboard block as its own scorecard section); src/utils/sniper_points.py (robust free-text price extraction fallback, e.g. excluding numbers after 'MA'); src/analyzer.py (check_content_integrity defines mandatory vs optional dashboard fields)

Gap verdict: **partial** (effort M, recommended True).  The building blocks of a 'decision scorecard' are scattered and real (thesis tag, rationale, confidence, single-level stop/target prices, red-team verdict, override receipts, a weight-normalization pattern, matured outcome tracking, notify() channels) — but they are NOT unified into one validated, renderable JSON artifact the way the candidate describes. Four concrete gaps: (1) no single `Dashboard`-shaped schema/type that bundles core_conclusion + data_perspective (MA table, volume) + battle_plan + action_checklist + signal_attribution + disagreement chain as one object with build-time invariants — the app's convention is instead many independently-optional fields appended incrementally across the pipeline; (2) sniper_points only has one entry level (referencePrice/limitPrice) plus one stop and one target — no ideal_buy vs secondary_buy distinction; (3) no per-proposal action_checklist of pass/warn/fail precondition items — policy gate results exist as strings/reasons, not a structured checklist array; (4) no technical/news/fundamentals/market signal_attribution weights normalized to sum to 100 and persisted per-proposal (the existing normalizeWeights in market.ts operates on a different, 8-factor scoring-weight space at scan time, and its output isn't attached to the final TradeProposal); (5) the override/disagreement trail (redTeamVerdict.overridden, humanOverrideApplied, finalSizeReview, socraticOverride.applied) is real but is a set of loose flags, not a Literal-typed contiguous adjustment chain validated at construction time (extra='forbid' equivalent, contiguity check).

Implementation sketch:
Do NOT build a Python-pydantic-style monolithic schema authored in one LLM call — that fights this app's actual pattern of incrementally-appended, optional, typed receipts persisted across the strategy loop (see the entryRegimeSeverity precedent explicitly deferring exactly this). Instead:
1. Add a `ProposalScorecard` interface in src/lib/types.ts, additive/optional on TradeProposal (mirrors sizingSnapshot/finalSizeReview pattern): `{ coreConclusion: { thesis: string; noPositionAdvice: string; hasPositionAdvice: string }; dataPerspective: { maAlignment: 'above_both'|'below_both'|'mixed'|'unknown'; priceVsMa: { price: number; sma50?: number; sma200?: number }; volume: { current: number; avg20d?: number } }; sniperPoints: { idealBuy?: number; secondaryBuy?: number; stopLoss?: number; takeProfit?: number }; actionChecklist: { id: string; label: string; status: 'pass'|'warn'|'fail' }[]; signalAttribution: { technical: number; news: number; fundamentals: number; market: number } }`.
2. Populate it deterministically in src/lib/strategy.ts alongside existing proposal construction — maAlignment/priceVsMa/volume come from already-computed indicators.ts sma50/sma200 and MarketQuote.volume (no new data source, no fabricated numbers — omit fields Yahoo/enrichment doesn't actually have, never fake a '0'). sniperPoints.idealBuy/secondaryBuy can reuse referencePrice and a policy-configurable pullback offset (owner-adjustable knob in TradingPolicy, e.g. `secondaryBuyPullbackPct`, default off/undefined — never a silent hard-coded number).
3. signalAttribution: compute from the SAME `factors`/factorBreakdown MarketQuote already carries (map liquidity/momentum→technical, sentiment/newsSent→news, value/quality/fcf/de→fundamentals, positioning/marketBreadthPct→market), normalized to sum to 100 with a small pure function in market.ts modeled directly on the existing `normalizeWeights` (same safeWeight/fallback-to-default pattern) — reuse the pattern, don't invent a new one.
4. actionChecklist: derive from the SAME policy-gate reasons/humanReviewReasons/redTeamVerdict already computed per proposal — map each independent gate (entry-drift, wash-sale, daily cap, red-team availability) to a {id,label,status} row instead of inventing new checks. This makes it a rendering of existing gate state, not a new authority.
5. Disagreement chain: add a small typed union in types.ts, e.g. `type DecisionStep = 'proposed'|'red_team_reject'|'override_requested'|'override_applied'|'human_approved'|'final'` and a `decisionChain: DecisionStep[]` built by appending one entry at each point the strategy loop / approval route already sets redTeamVerdict.overridden, humanOverrideApplied, or socraticOverride.applied — with a small pure validator (contiguity check: each step differs from the last, 'override_applied' only appears if 'override_requested' preceded it) called once at persistence time in db-proposals.ts, throwing/logging rather than silently accepting a malformed chain. Persist via the existing db-proposals.ts / db-socratic.ts modules (JSON column, same as sizingSnapshot).
6. Render as a new con-* component (app/console/components/proposal-scorecard.tsx) using existing con-card/con-chip primitives — a collapsible block inside approval-card.tsx and a read-only view in the decision-case drawer, not a new page.
7. Digest delivery: add an OPT-IN daily notify() message type ('scorecard_digest') gated by a new user-adjustable notification_prefs toggle (off by default, like every other notify() channel) — summarize the day's scorecards through the existing notify() dispatcher (push/email/webhook), no new channel infrastructure.
8. Grading: extend outcome-engine.ts to optionally compare sniperPoints.stopLoss/takeProfit against the matured outcome bars already fetched (OutcomeOHLCFetcher) — a pure additive comparison, not a new fetch pipeline.
Everything above is additive/optional on already-computed values; nothing requires a new provider call, a new LLM round-trip, or fabricated data — if a field (e.g. avg20d volume) isn't actually available, omit it rather than fake it, per the no-mock-data rule.

### llm-output-repair-ladder - IMPLEMENTED
**Post-generation consistency repair with an auditable, named adjustment log (score-action contract, phase-fact checks, per-field fallback cascade)**

Three deterministic post-hoc passes treat the LLM's structured output as untrusted and repair it per-field rather than rejecting or blind-trusting: (1) a canonical score-band-to-action table is injected into the prompt AND re-verified after generation - a neutral action paired with a directional score is overridden to match the score unless the model supplied an explicit guardrail_reason for the divergence; (2) a market-phase guardrail checks the text against ground truth - 'buy now' language during premarket/closed sessions is rewritten to a wait state, postmarket-recap phrasing generated mid-session is replaced, and self-reported 'high' confidence is capped when core data blocks came back degraded; (3) a per-field degradation ladder fills any missing mandatory field first from an independently computed technical result (rule-based trend label, computed support level for stop_loss) and only then from an honest localized 'model did not provide X' placeholder - never a fabricated value, never a silently absent key.  Critically, every override is recorded as a named adjustments entry (e.g. non_intraday_action_adjusted, confidence_capped_core_data_degraded) appended to the delivered report's data_limitations, so corrections are visible, not silent edits.  This is correctness hardening, not paternalism - it never blocks a decision, it makes the numbers and the words agree and shows its work, consistent with ST's no-fake-data rule.

External-repo evidence: src/schemas/decision_scale.py (score-band table injected into prompt and enforced via score_action_conflicts_without_guardrail); src/phase_decision_guardrail.py (temporal-hallucination detection, confidence capping, named adjustments log); src/analyzer.py + src/core/pipeline.py (check_content_integrity, _backfill_agent_dashboard_fields, apply_placeholder_fill three-tier cascade)

Gap verdict: **partial** (effort M, recommended True).  Three sub-pieces, three different states. (1) Score-action contract: N/A by design — ST's schema makes side (buy/sell/short/cover) the action itself, so a 'neutral action with directional score' conflict cannot arise; no gap to close here. (2) Market-phase guardrail: MISSING outright — no deterministic check anywhere in the proposal pipeline compares rationale phrasing against the actual market session (closed/pre/regular/post), and the already-computed DataCompletenessReport / per-symbol EnrichmentSourcedField data (which exist and would be the ideal input for confidence-capping on degraded data) are never read by strategy.ts or strategy-risk.ts — they only feed an admin dashboard. Since the scheduler ticks every 60s across all sessions and the app explicitly supports extended-hours trading, a Bull-step rationale COULD emit session-incongruous language ('buying at the open,' a postmarket recap tone mid-session) with nothing catching it, and a proposal generated on thin/degraded data currently gets exactly the same confidence treatment as one generated on full data. (3) Per-field fallback cascade + named-adjustments log: PARTIAL — a real, independently-computed fallback ladder (ATR-scaled > beta-scaled > flat) already exists but only for bracket stopLoss/takeProfit prices, and its disclosure is a free-text append to `rationale` rather than a structured, queryable list; everywhere else, an incomplete/invalid LLM-repaired proposal is DROPPED wholesale (filterRepairedProposals) rather than field-repaired, and other missing fields get static defaults (timeInForce ?? 'gfd') rather than an independently-computed value. The app does already have the exact STRUCTURAL PATTERN the lesson wants (`preVetoReasons: string[]`, kind-prefixed tags) — it's just wired to allow/block decisions, not to field-level repair receipts.

Implementation sketch:
Scope down to the two real gaps (skip the score-action piece — it doesn't apply to this schema) and reuse existing idioms rather than building parallel infrastructure:

1. Data-degradation confidence cap (src/lib/strategy-risk.ts, alongside the existing calibratedConviction/convictionCapUncorroborated block at ~line 486-507): add a new policy.tuning knob (e.g. `confidenceCapDataDegraded`, default a conservative on-by-default like the existing convictionCapUncorroborated pattern) that reads each candidate's SymbolEnrichment/EnrichmentSourcedField sourcing (src/lib/data-providers.ts) at proposal time — if the core fields the thesis leans on (price, technicals, or whatever tradeThesisTag implies) came back from a degraded/fallback tier rather than a primary source, cap confidenceScore's upside contribution the same way the realized-edge cap does today. This is a real gate on the numbers, not a text check, and it's cheap: the sourcing data is already computed per-run in the market scan, just never consumed for this purpose.

2. Session-text sanity check (new small function, e.g. src/lib/proposal-phase-guard.ts, called from strategy.ts right after the Bull/Green step parses each proposal, before sanitizeProposals): deterministic regex/keyword check comparing the proposal's rationale text against `currentMarketSession(now)` (src/lib/market-hours.ts, already exists) — flag (not silently rewrite) phrasing like "buy now"/"at the open" during a closed/pre session, or postmarket-recap phrasing mid-session. Given ST's "guardrails are adjustable preferences, never a scolding block" philosophy, this must NOT block or rewrite the proposal — it should append a receipt, matching how enrichOpeningProposal already discloses fallbacks via rationale text.

3. Structured adjustments log: extend TradeProposal (src/lib/types.ts, near `preVetoReasons`) with a new optional `dataAdjustments?: string[]` (or reuse/rename preVetoReasons' kind-prefix convention, e.g. `stop_fallback_atr: ...`, `confidence_capped_degraded_data: ...`, `session_phrase_mismatch: ...`) so the existing free-text rationale appends (bracket-stop fallback, marketable-limit conversion, non-bracket-broker disclosure) AND the two new checks above all land in one machine-queryable array — persisted for free since TradeProposal already serializes as JSON in db-proposals.ts. Surface it on the approval card (existing con-* console component that already renders redTeamVerdict/preVetoReasons) as a small receipts list, and optionally roll a count into admin/data-catalog or a new admin panel.

Effort breakdown: knob + cap logic in strategy-risk.ts (~0.5 day, mirrors existing code closely); session-text guard as a new small pure function + call site + tests (~0.5 day); TradeProposal field + db-proposals.ts JSON passthrough + approval-card UI receipt (~0.5-1 day); test coverage across all three (~0.5 day). Total lands in the M band.

### news-intel-fanout-quality-bar - IMPLEMENTED
**Dimensioned news-search fan-out with a rule-based relevance scorer and a provider quality tournament**

Per symbol per run, the pipeline fires 5-6 distinct searches, each an intelligence dimension with its own query template and freshness policy: breaking news (strict recency), analyst/earnings/industry context (180-day lookback), risk_check (insider selling / lawsuits, strict recency), and official announcements (query targets exchange/filing sites), with wholesale query rewrites for ETFs (tracking error / NAV language).  Every raw hit then passes an explainable additive relevance scorer - points for ticker/company-name hits in title vs snippet vs URL, a denylist for ambiguous common-word company names (apple, meta, square, target, gap) that only score when a corroborating event term (earnings/guidance/lawsuit) co-occurs, and a human-readable relevance_reasons list rendered into the LLM prompt so the model sees why each item was kept.  Provider selection is a quality tournament, not first-success failover: a provider's technically successful response is only accepted if it contains at least one direct-company hit; otherwise the best-scoring response across all providers wins.  A spam gate with a hard allowlist for official sources (sec.gov, exchange sites) runs before context assembly.

External-repo evidence: src/search_service.py:3162-3336 (_score_news_relevance additive rubric + ambiguous-name denylist); src/search_service.py:4350-4602 (search_comprehensive_intel per-dimension templates, freshness windows, provider round-robin); src/search_service.py:3993-4283 (quality-bar tournament, _is_better_ranked_news_response); src/search_service.py:3403-3466 (_filter_ranked_news_for_context with official-source allowlist)

Gap verdict: **partial** (effort M, recommended True).  ST already has multi-provider news/sentiment fan-in (Alpha Vantage, Finnhub, Marketaux, Alpaca stream) merged through a priority-ordered cascade, keyword-based sentiment scoring, and prompt-safe headline dedup/compaction — but it has no entity-relevance layer at all: two of its own providers (Alpha Vantage, Marketaux) already return a per-article relevance/match score in their API responses and ST silently discards both, so a headline that only tangentially mentions the ticker (AV relevance_score near 0, or a weak Marketaux match_score) is treated identically to a strong direct hit and can reach the LLM prompt un-flagged. There is no ambiguous-common-word denylist (Apple/Meta/Square/Target/Gap-style tickers are exactly the ones ST's own watchlist can hold — e.g. META, TGT), no explainable relevance-reasons surfaced to the prompt, and the field merge across providers is first-wins-by-priority rather than a best-of comparison. The lesson's core 'dimensioned search fan-out with per-dimension query templates and freshness windows' does NOT map cleanly onto ST's architecture, though, because ST never does free-text web search for news — it uses ticker-parameterized provider APIs where the provider does (partial) entity matching server-side, and the 'official announcements' dimension is already better covered by direct SEC EDGAR 8-K ingestion than a search-engine allowlist gate would be. So the transferable value is narrower than the source lesson: adopt the explainable-relevance-scorer-plus-denylist-plus-quality-comparison pattern, not the search-fan-out mechanism.

Implementation sketch:
1) New leaf module src/lib/news-relevance.ts (mirrors prompt-headlines.ts's no-imports leaf style): scoreHeadlineRelevance(headline, symbol, companyName, opts) -> {score, reasons[]} — additive rubric (ticker token match, company-name-in-title match), plus an owner-editable ambiguous-name denylist entry (e.g. {name:'meta', requiresCorroboration:['earnings','guidance','lawsuit','recall','downgrade','insider']}) that only scores a bare common-word company name when a corroborating event term co-occurs in the same headline; returns human-readable reasons for debuggability (used in logs/ops snapshot, not shown per-headline in the prompt today). Cover with deterministic unit tests.
2) Wire ALREADY-AVAILABLE provider scores first (cheapest slice): in AlphaVantageEnrichmentProvider (data-providers.ts ~4364-4402), read ticker_sentiment[].relevance_score per feed item and only fold ticker_sentiment_score / keep the headline title when relevance_score clears a threshold. In marketaux-provider.ts, add match_score to MarketauxEntity and gate aggregateMarketauxBySymbol's headline collection and sentiment accumulation on it the same way.
3) For providers with no native relevance score (Finnhub company-news, Alpaca/Benzinga stream via news-store.ts), call scoreHeadlineRelevance() against the headline title before it's stored/returned as a SymbolEnrichment.headlines entry.
4) Owner-adjustable settings (db-settings.ts, following the iraWashSaleHandling pattern — default ON but a real off-switch, never a silent hard block): a newsRelevance settings block with enabled (default true), minRelevanceScore (default e.g. 0.35), and an editable ambiguousNameDenylist (JSON array), persisted via db.ts migrate() + CRUD in db-settings.ts. Expose via a small con-* settings panel under /console/connections or a new /console/data-sources section so the owner can tune the threshold/denylist without a redeploy.
5) Cascade merge upgrade (optional follow-up, higher risk): change CascadingEnrichmentProvider's headlines/sentiment resolution from strict first-wins-by-priority to compare each configured provider's average relevance score for the symbol this run and prefer the higher-scoring set — small scoped diff near data-providers.ts ~1550-1700, guarded by its own settings toggle since it changes existing source-attribution semantics (MarketScan.source string).
6) No fake data: a symbol with zero headlines surviving the relevance filter gets {} exactly like today's 'no coverage this cycle' case — never a fabricated backfill. No new scheduler lane or cron needed (filter runs synchronously inside the existing per-provider fetch path); no new notify() channel needed, though a low-relevance-dropped counter could feed the existing api_health_log/ops-snapshot machinery for visibility.
7) Tests: extend marketaux-provider.test.ts / data-providers tests asserting a low-match_score/low-relevance_score entity is excluded from both headlines and sentiment average, plus a new news-relevance.test.ts for the denylist rubric.

### social-sentiment-context - PLANNED (deferred, board row exists)
**Reddit, X, and Polymarket per-ticker sentiment block merged into analysis context**

A SocialSentimentService pulls three per-ticker signals from one aggregator API: a Reddit report (buzz score /100, sentiment score, 7-day mention and subreddit counts, top 5 mentions with per-mention sentiment, 5-day daily history), plus cached (10-min TTL, single-flight deduped) X/Twitter trending and Polymarket prediction-market data (buzz, market sentiment, trade count) filtered to the ticker.  All three render into one formatted text block concatenated onto the news context before it reaches the LLM, gated to US tickers only.  A _coalesce helper explicitly preserves 0 as a valid neutral sentiment rather than treating falsy as missing.  Polymarket implied odds as a sentiment input is the novel piece - a real-money crowd signal, not scraped chatter, which fits ST's real-data-only rule.  ST has congress-trade signals but no retail/social/prediction-market sentiment axis at all.

External-repo evidence: src/services/social_sentiment_service.py:55-343 (three endpoints, TTL cache, _format_social_intel, zero-preserving _coalesce); src/core/pipeline.py:650-661 and 1372-1386 (US-only gate, injection into news_context in both pipeline and agent modes)

Gap verdict: **missing** (effort M, recommended True).  Nothing implementing any piece of this lesson exists. ST's `sentiment` field is news-article tone (Finnhub / Alpaca-Benzinga / Marketaux / Alpha Vantage, all cascaded in data-providers.ts), `insiderSentiment` is SEC Form 4 derived, and congressional `netSentiment` is trade-flow derived — three distinct, already-covered sentiment axes, none of which touch retail social chatter (Reddit/X) or prediction-market odds (Polymarket). (3) register in src/lib/data-catalog.ts and src/lib/source-capability-matrix.ts under the existing `sentiment_events` category so provenance/Connections-page attribution works for free; (4) add a `sentimentTitle`-style formatter in dashboard-ui.ts for the Market Scan table cell; (5) format a text block (buzz score, mention counts, top mentions, Polymarket implied odds) and append it into the news/evidence context alongside `compactHeadlinesForPrompt` output at the existing injection points in strategy.ts (~4950-4953, 5506-5507, 6266-6278) — this is genuinely a small, additive change since the headline-injection scaffolding already exists; (6) gate to US tickers only using whatever exchange/country signal MarketQuote already carries (check quote.sector/exchange fields — no new gating infrastructure needed, mirror the pattern used for the FMP economic-calendar US-only gate); ### strategy-overlay-library - PLANNED (deferred, board row exists)
**Hot-loadable natural-language strategy template library with regime-tagged auto-routing**

Each of ~15 strategies (golden cross, box oscillation, sector leadership, event-driven, growth quality, etc.) is a YAML file with structured frontmatter (name, market_regimes tags, required_tools, core_rules citations) plus a freeform natural-language instructions block injected verbatim into a sub-agent prompt - no code per strategy.  Users add or override strategies by dropping a file into a directory (env-configurable path, name collision overrides built-ins); no deploy.  A SkillRouter infers a regime tag (trending_up/down, sideways, volatile, sector_hot) from the technical picture and auto-selects the 1-3 strategies whose declared market_regimes match, falling back to a priority-ordered default set.  For ST the right transfer is an advisory overlay layer, not a replacement for computed indicators: owner-editable heuristic templates (sector rotation, event-driven, earnings-season posture) that annotate the deterministic proposal, with a lightweight regime classifier deciding which lenses get emphasized in the prompt per run.  This matches ST's guardrails-as-adjustable-owner-preferences philosophy: strategy emphasis becomes data the owner edits, not code an agent redeploys.

External-repo evidence: strategies/README.md + strategies/*.yaml (frontmatter + freeform instructions format, core_rules numbered-taxonomy citations); src/agent/skills/base.py (SkillManager.load_custom_skills, drop-in override); src/agent/skills/router.py + src/agent/skills/defaults.py (regime inference and market_regimes matching)

Gap verdict: **partial** (effort M, recommended True).  The app has substantial regime-awareness and owner-editable strategy infrastructure, but not the specific mechanism the lesson describes: a hot-loadable library of MULTIPLE named strategy templates with structured frontmatter (market_regimes tags, required_tools, core_rules citations) plus freeform instructions, auto-routed by a regime classifier that picks 1-3 concurrently-emphasized lenses per run with a priority-ordered fallback.

What's missing specifically: (1) no file/DB-backed collection of discrete, independently-taggable strategy templates — strategy_profiles is one full prompt+policy+weights bundle, manually activated, one-at-a-time, not several composable regime-tagged overlays layered onto a single run; (2) no SkillRouter — nothing infers a regime and automatically selects/injects the matching subset of templates into the prompt each run; today regime selection of ANYTHING is a manual owner action (activateStrategyProfile via API/UI) or a fixed always-present block (ownerCoaching, thesis scorecards); (3) no structured per-template frontmatter (regime tags, required tools, rule citations) — strategy_profiles rows are just {name, full prompt text, policy, scoringWeights}; (4) no fallback/priority-ordered default set when nothing matches a regime.

Implementation sketch:
Add a new, purely-additive overlay layer that composes ON TOP of the existing single strategyPrompt/active-profile — do not touch strategy_profiles' semantics.

1. Schema (src/lib/db.ts migrate()): new table `strategy_overlays` (id, user_id, name, market_regimes TEXT [JSON array of MarketRegime enum values, or "any"], instructions TEXT [freeform, owner-authored], priority INTEGER, enabled INTEGER DEFAULT 1, created_at, updated_at). CRUD lives in a new src/lib/db-overlays.ts module per the db-* split convention (listStrategyOverlays/createStrategyOverlay/updateStrategyOverlay/deleteStrategyOverlay), re-exported from db.ts's barrel.

2. Router (new src/lib/overlay-router.ts, dependency-light like market-regime.ts): `selectActiveOverlays(overlays, regime, maxCount)` — filters enabled overlays whose market_regimes includes the current classifyMarketRegime(...).regime or "any", sorts by priority, takes top N (owner-configurable via a new `policy.tuning.maxActiveOverlays`, default e.g. 2), falls back to a priority-ordered default set (or empty) when nothing matches. ### bayesian-strategy-trust-weights - PLANNED (deferred, board row exists)
**Sample-gated, horizon-bucketed Bayesian shrinkage for per-strategy trust, with a bounded multiplier**

Every strategy opinion is persisted immutably and later graded against realized forward price movement at fixed horizons (1d/3d/5d/10d) into hit/miss/observational/pending/unable outcomes, bucketed strictly by (strategy, horizon, engine_version) - never pooled.  A bucket only influences live weighting once it reaches 30+ evaluated samples; below that it returns a neutral factor of exactly 1.0 rather than an unreliable estimate.  Qualified buckets shrink the raw hit rate through a symmetric Beta(15,15) prior, discount by an unable_rate penalty, and combine into a performance_factor clamped multiplicatively to [1/1.2, 1.2] that scales that strategy's confidence in future aggregation - so no strategy is ever zeroed out or allowed to dominate off a streak.  A companion aggregation rule set forbids reporting 'high consensus' from fewer than 2 valid opinions or zero total confidence.  For ST this is a concrete, auditable calibration mechanism to compare against its existing crossover-learning confidence-size-cap: the sample-floor, symmetric prior, and bounded-ratio clamp are exactly the anti-overfit guards a real-money learning loop needs.

External-repo evidence: docs/multi-strategy-contract.md (grading taxonomy, Beta(15,15) shrinkage, performance_factor clamp, consensus invariants incl. 'zero evidence -> insufficient'); src/agent/skills/aggregator.py (evidence-chain vs diagnostics partition, consensus_level hard rules)
