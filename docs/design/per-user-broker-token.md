# Scope: Per-user broker token (Robinhood) + per-user broker linking

_Scoped 2026-06-21 (multi-agent design pass). Effort: **s** · Autonomy: **autonomous-after-decisions**_

## Current state
WHAT EXISTS:

1. `src/lib/mcp-oauth.ts` — three process-global string constants (lines 3-5):
   - `CLIENT_SETTING = "robinhood_mcp_oauth_client"` (shared OAuth client registration)
   - `STATE_PREFIX = "robinhood_mcp_oauth_state:"` (shared PKCE state namespace)
   - `TOKEN_SETTING = "robinhood_mcp_oauth_tokens"` (shared token store)
   All three are read/written into the shared `settings` table via `getInternalSetting`/`setInternalSetting` (`db.ts:551-567`), which is a simple key-value table with no `user_id` column — one row per key, globally visible.

2. `app/api/auth/robinhood/start/route.ts` (line 6-11) — `GET()` calls `buildMcpAuthorizationUrl()` with no userId anywhere. The state PKCE blob saved at `mcp-oauth.ts:58` is keyed only by the random state value, not by userId.

3. `app/api/auth/robinhood/callback/route.ts` (line 6-26) — `GET()` calls `completeMcpOAuthCallback()` with no userId. On success, calls `setMcpOAuthTokens(tokens)` (`mcp-oauth.ts:115`) which writes `TOKEN_SETTING` — one global key, any user's flow overwrites all others.

4. `src/lib/robinhood.ts:279,329,346` — `callRobinhoodMcpMethod` and `getRobinhoodMcpHealth` call `getMcpAccessToken()` and `clearMcpOAuthTokens()` with no userId. One token is returned for any caller regardless of which user initiated the OAuth flow.

5. `src/lib/broker.ts:5` — `getBrokerGateway(policy, userId)` receives a `userId` parameter but passes it to `getAlpacaGateway(userId)` only; `getRobinhoodGateway()` (line 14) takes no arguments, cannot accept a userId, and produces an `HttpMcpRobinhoodGateway` that internally calls the global `getMcpAccessToken()`.

6. `app/api/broker/mcp/health/route.ts` — calls `getRobinhoodMcpHealth()` with no userId; health check uses the global token.

WHAT IS MISSING (the gap):

- The `settings` table (`db.ts:58`) has no `user_id` column; `getInternalSetting`/`setInternalSetting`/`deleteInternalSetting` are single-key, no-user-scope helpers. Per-user OAuth storage requires either a new keying convention (e.g., `robinhood_mcp_oauth_tokens:userId`) or a new dedicated table.
- `buildMcpAuthorizationUrl()` does not accept/embed userId; the PKCE state blob cannot be traced back to the initiating user at callback time.
- `completeMcpOAuthCallback()` does not know which user completed the flow; it cannot write a per-user token.
- `getMcpAccessToken()`, `clearMcpOAuthTokens()`, `setMcpOAuthTokens()`, `getStoredMcpOAuthTokens()` are all stateless with respect to userId.
- `getRobinhoodGateway()` (`robinhood.ts:39`) is a no-arg factory; `getBrokerGateway` (`broker.ts:14`) calls it without forwarding the already-present `userId` parameter.
- Auth/session plumbing DOES exist: `middleware.ts` is fully implemented (Auth.js Google path + dev fallback); `resolveRequestUserId()` correctly derives userId from the `x-authenticated-user-email` header; `identity.ts` maps email→stable userId. The start/callback routes simply never call `resolveRequestUserId`.
- The `connected_accounts` table (`db.ts:164`) is already per-user (has `user_id NOT NULL` + index), so Robinhood account metadata can be stored per-user today — the missing piece is only the OAuth token itself.

## Recommended approach
Key all three mcp-oauth constants by userId using a thin namespacing convention: replace the three bare constants with functions that return `${PREFIX}:${userId}` strings (e.g., `tokenSettingKey(userId)`, `stateKey(state, userId)`, `clientSettingKey(userId)`). Pipe userId through `buildMcpAuthorizationUrl(userId)` and `completeMcpOAuthCallback({code, state, userId})`. Embed userId into the PKCE state blob (`McpOAuthState.userId`) so the callback can recover it without a second lookup. Thread userId through the two route handlers (`start` and `callback`) via `resolveRequestUserId(request)`. Make `getMcpAccessToken(userId)`, `clearMcpOAuthTokens(userId)`, and `setMcpOAuthTokens(userId, tokens)` accept userId; update `getRobinhoodGateway(userId)`, `getRobinhoodMcpHealth(userId)`, `callRobinhoodMcpMethod(userId, ...)`, and the `broker.ts` `getBrokerGateway` call site to forward userId. Preserve the existing `ROBINHOOD_MCP_AUTH_TOKEN` env-var override as a global fallback (it already short-circuits at `mcp-oauth.ts:99`) — process-env tokens are still valid for single-user/operator deployments. No schema migration is needed because the `settings` table key is just a string; namespacing via `:userId` suffix is a pure-application-layer change with no DDL. The client registration (`CLIENT_SETTING`) can reasonably remain global (one app-level client, keyed by `clientSettingKey("_app")`) or be per-user — document the tradeoff and let the owner decide.

## Owner decisions needed
- State-recovery approach at callback time: (a) scan `settings WHERE key LIKE 'robinhood_mcp_oauth_state:%:${randomPart}'` — clean but adds a LIKE query per OAuth completion; or (b) embed userId into the `state` URL parameter as `${userId}:${randomPart}` — simpler but leaks the internal userId (a `u_<24hex>` opaque hash) in the authorization redirect URL. Decision affects mcp-oauth.ts and the callback route.
- OAuth client registration scope: should CLIENT_SETTING be per-user (`robinhood_mcp_oauth_client:${userId}`) so each user registers their own client, or per-app (a single `robinhood_mcp_oauth_client:_app` shared by all users)? Per-user is more isolated but causes N client registrations at the broker; per-app is fine if Robinhood MCP allows shared client IDs across users (likely yes — one Agentic Trading app client, multiple user tokens). The `ROBINHOOD_MCP_CLIENT_ID` env override already covers the pre-registered case.
- Global env-var token fallback: `ROBINHOOD_MCP_AUTH_TOKEN` currently acts as a process-level override that bypasses all per-user lookup (mcp-oauth.ts:99). In a multi-user deployment this means ALL users share that token regardless of their own OAuth state. Decide whether to keep it as a global admin override, make it a per-user-noop in multi-user mode, or document it as a single-user-only env var that should not be set in multi-tenant deployments.
- Whether this slice lands before or after M6 full auth (Auth.js Google). The middleware and identity chain already exist; `resolveRequestUserId` is trusted in production after middleware verifies the Auth.js session. Per-user broker tokens work correctly as soon as the session is trusted. In dev (no Auth.js config), `resolveRequestUserId` returns `DEV_USER_ID` ('local') for all requests, so per-user linking is a no-op in local dev — clarify whether that is acceptable or whether dev needs a way to simulate multiple users.

## Risks
- State recovery at callback time is the only genuinely tricky part. The OAuth `state` parameter arrives at the callback with no session cookie (the redirect comes from Robinhood's server, not the user's session), so there is no `x-authenticated-user-email` header to derive userId from. If approach (b) is not chosen, the scan-based approach must be robust to prefix collisions (mitigated by 32-byte random suffix) and to orphaned state blobs from abandoned flows (add a createdAt TTL sweep — already in McpOAuthState.createdAt but currently never enforced).
- A 401 from the MCP endpoint currently calls `clearMcpOAuthTokens()` globally (robinhood.ts:346). After this change it must call `clearMcpOAuthTokens(userId)`. If userId is somehow wrong (e.g., userId resolution diverges between the initiating request and the MCP call), only the wrong user's token is cleared — a silent fail-open. Mitigate by tracing userId through consistently and adding a test.
- The `ROBINHOOD_MCP_AUTH_TOKEN` env-var override at mcp-oauth.ts:99 bypasses all per-user logic. In a multi-user production deployment where this var is set, all users silently share that token — a potential cross-user data exposure. The risk is low in the current single-operator deployment but must be documented explicitly.
- The `settings` table key-value store has no TTL mechanism. Orphaned state blobs (from abandoned OAuth flows) accumulate. Low impact now but should have a sweep or TTL check added alongside this work.
- The design doc (chat-multiuser-learning-design.md §2.2 item 4) lists per-user broker token as a LATER milestone, after auth lands and is trusted. Auth middleware IS already live (middleware.ts, identity.ts, request-user.ts are all implemented). Confirm with the owner that this can ship now rather than waiting for a future M6 milestone.

## Dependencies
Auth middleware and identity chain must be trusted in production before per-user tokens are meaningful. This is already met: `middleware.ts` is implemented, `AUTH_SECRET` enables the trusted Auth.js Google path, and `resolveRequestUserId` correctly derives userId from `x-authenticated-user-email`. No other code changes need to land first. The `connected_accounts` table already has `user_id NOT NULL` so Robinhood account metadata is already per-user — this item only closes the OAuth token storage gap.

## Post-merge hardening (2026-06-21, after PR #42 / commit `0056f04`)
An adversarial audit of the merged feature found a tenant-isolation gap in two **read-only enrichment paths** that called the `fetchRobinhood*` helpers with no userId, so they fell through to `opts.userId ?? DEV_USER_ID` (`'local'`) and silently used the operator's broker token for every user — exactly the implicit-`'local'` variant of Risk #3 below. Fixed (branch `fix/per-user-robinhood-enrichment-token`; rollout `docs/rollouts/2026-06-21-robinhood-enrichment-token-isolation.md`):

- `fetchRobinhoodHistoricals` / `fetchRobinhoodFundamentals` (`robinhood.ts`) now take a **required** `userId` — no `DEV_USER_ID` default — so the compiler forbids a silent `'local'` fallback.
- `fetchDailyOHLC` (`history.ts`) consults the private Robinhood tier **only when an explicit userId is in scope** and forwards it. The computed-technicals refresh (`web-sources/technical.ts`) writes a **global** dataset and has no per-user context, so it omits the broker tier entirely (public Yahoo/Stooq still populate it — no regression) rather than borrowing `'local'`.
- `RobinhoodEnrichmentProvider` (`data-providers.ts`) takes the request-scoped userId (wired from `getEnrichmentProvider(userId)`, matching every other provider), threads it into the fundamentals fetch, and **fails closed** (empty enrichment, no broker call) when no user is in scope.
- **Callback session binding** (closing Risk #2's residual): `completeMcpOAuthCallback({ ..., expectedUserId })` now rejects a state whose `userId` doesn't match the completing session (`resolveRequestUserId(request)` in the callback route). The state row is consumed before the check, so a mismatched attempt can't be replayed. This blocks binding a freshly-minted token under a victim's userId via an attacker-initiated flow.

Regression coverage: `test/robinhood-tenant-isolation.test.ts` (7 tests) — user B never resolves user A's (`'local'`) token via historicals, fundamentals, the enrichment provider, or the OHLC cascade; the no-user pass fails closed; and the callback rejects a cross-session state. **Still open:** the `ROBINHOOD_MCP_AUTH_TOKEN` env override (Risk #3) is a deliberate global bypass and must not be set in a multi-user deployment; the orphaned-state TTL sweep (Risk #4) remains unenforced.
